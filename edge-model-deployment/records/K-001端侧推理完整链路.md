# 端侧程序如何把模型部署各环节串起来

理解端侧模型部署，最重要的不是记住某个框架的 API，而是先看清一条稳定的数据流。一个训练完成的模型真正进入端侧程序后，并不是“把图片交给模型文件，模型文件直接返回业务答案”，而是由端侧程序负责把模型文件加载到 Runtime 中，再把原始业务数据转换成模型能够接收的 Tensor，执行一次 Forward/Inference，拿到输出 Tensor，最后通过后处理把这些数值转换成业务程序真正能使用的结果。

整条主链路可以先记成：

```text
模型文件
  ↓ 加载
Runtime 中的可执行模型

原始业务输入
  ↓ 预处理
Input Tensor
  ↓ Inference / Forward
Output Tensor
  ↓ 后处理
业务结果
```

这条链路里其实包含两类工作：一类通常在初始化时只做一次，例如读取模型文件、创建 Runtime、建立 Session 或执行上下文、准备输入输出资源；另一类会随着每一张图片、每一帧音频或每一批传感器数据不断重复，也就是预处理、写入 Input Tensor、执行推理、读取 Output Tensor 和后处理。

## 模型文件为什么不能自己直接完成推理

模型文件本质上是模型的静态表示。它通常保存了网络结构、权重参数以及运行时需要的其他模型信息，但文件本身不会主动执行任何计算。就像一个可执行程序的二进制文件需要操作系统和 CPU 来真正执行一样，模型文件也需要一个 Runtime 把这些静态描述解释成一次真实的计算过程。

Runtime 的职责可以理解成“模型执行器”。它读取模型文件，理解其中有哪些算子、参数、输入和输出，然后在 CPU、GPU、NPU 或其他可用计算后端上组织这些算子执行。不同框架的 API 名称会不同：有的叫 Session，有的叫 Interpreter，有的叫 Net 或 Executor，但这些名称背后的核心职责类似——加载模型、准备执行环境、接收输入 Tensor、触发推理并提供输出 Tensor。

因此，模型文件和 Runtime 的关系可以理解成：

```text
模型文件 = 保存好的模型
Runtime  = 真正执行这个模型的软件引擎
```

没有 Runtime，模型文件只是静态数据；没有模型文件，Runtime 也不知道应该执行哪一个神经网络。

## 原始业务数据为什么不能直接送进模型

真实程序拿到的数据通常不是模型训练时直接看到的形式。摄像头可能给你一张 `1920×1080` 的 BGR 图片，模型却可能要求 `640×640`、RGB、`float32`、数值范围 `[0,1]`，甚至要求 Tensor 的 shape 是 `[1,3,640,640]`。

所以预处理的本质并不是“图像处理附加步骤”，而是在完成一次接口适配：把业务世界中的原始数据转换成模型输入契约要求的数据表示。

例如一张图片可能经历：

```text
摄像头图像
1920×1080 / BGR / uint8
        ↓ resize
640×640
        ↓ BGR → RGB
RGB
        ↓ uint8 → float32
float32
        ↓ normalize
0~1 或其他训练时约定范围
        ↓ layout / shape 调整
[1, 3, 640, 640]
```

预处理最终的产物不是“处理过的图片”这个模糊概念，而是一个满足模型输入要求的 **Input Tensor**。这个 Tensor 的 shape、dtype、数据排列方式和数值分布必须与模型训练和导出时约定的输入一致，否则即使代码能够运行，模型结果也可能完全错误。

## Input Tensor 进入 Runtime 后发生了什么

Input Tensor 准备完成后，端侧程序会把它交给 Runtime，然后触发一次 Inference，也就是模型的 Forward。

这一阶段做的事情，就是按照模型定义好的网络结构，从第一层开始一层层计算。卷积层、线性层、激活函数、归一化层以及其他算子会依次处理 Tensor，训练阶段已经确定下来的权重参数在这个阶段保持不变。

可以把它理解成：

```text
Input Tensor
   ↓
Layer 1
   ↓
Layer 2
   ↓
Layer 3
   ↓
...
   ↓
Output Tensor
```

这里没有训练阶段的 Loss、Backward 和参数更新。部署程序只是在使用已经训练好的参数执行一次确定的前向计算。所以端侧部署代码里最核心的 Runtime 调用，通常就是某种 `run`、`invoke`、`forward`、`execute` 一类操作。

## 为什么 Runtime 输出的还是 Tensor

神经网络本质上做的是数值计算，因此它天然输出的也是 Tensor，而不是直接输出人类业务语义。

例如一个分类模型可能输出：

```text
[0.01, 0.03, 0.92, 0.04]
```

模型只是在表达四个类别对应的数值结果。至于索引 `2` 代表“猫”，这是业务侧或模型配套标签表赋予它的含义。

一个目标检测模型可能输出很多框坐标、置信度和类别分数；一个人脸特征模型可能直接输出一个几百维的向量；一个语音模型也可能输出 token 概率。这些结果仍然属于模型空间里的数值表达，而不是业务程序最终希望操作的对象。

因此 Runtime 的职责通常到 Output Tensor 为止。它负责正确执行模型，但不会替业务程序决定“多少置信度才算检测成功”“两个框是否应该做 NMS”“某个类别编号显示成什么名字”等业务规则。

## 后处理如何把 Tensor 变成业务结果

后处理负责完成最后一次接口转换：从模型输出空间回到业务语义空间。

例如分类模型可能执行：

```text
Output Tensor
[0.01, 0.03, 0.92, 0.04]
        ↓ argmax
类别 index = 2
        ↓ 查标签表
"cat"
```

目标检测模型则可能需要读取框坐标和类别分数，再做阈值过滤、NMS、坐标映射等操作，最终形成业务层方便使用的数据结构，例如：

```text
Detection {
    class_id: 2,
    label: "cat",
    score: 0.92,
    x: 120,
    y: 80,
    width: 200,
    height: 180
}
```

因此，后处理和预处理正好处于模型的两端：预处理负责把业务输入翻译成模型语言，后处理负责把模型输出重新翻译回业务语言。

## 初始化阶段和每次推理阶段要分开看

阅读真实端侧代码时，一个很容易混淆的地方，是把模型初始化和单次推理揉在一起理解。实际上它们通常是两个生命周期。

初始化阶段一般类似：

```text
读取模型文件
    ↓
创建 Runtime / Session / Interpreter
    ↓
加载模型
    ↓
准备输入输出信息和执行资源
```

这部分往往只在程序启动、模块初始化或者模型切换时执行一次。因为加载模型和准备执行环境通常存在明显开销，没有必要每处理一帧数据就重新做一遍。

而运行阶段则会不断循环：

```text
拿到一份原始输入
    ↓
预处理
    ↓
写入 Input Tensor
    ↓
执行 Inference
    ↓
读取 Output Tensor
    ↓
后处理
    ↓
交给业务层
```

如果输入来自摄像头，那么这个循环可能每秒执行几十次。模型和 Runtime 依然是之前初始化好的，只是 Input Tensor 中的数据不断变化，然后不断执行新的 Forward。

## 用一帧图片把整条链路走一遍

假设摄像头采集到一张图片，端侧程序希望判断里面有没有猫。

程序启动时先读取模型文件，创建 Runtime，并让 Runtime 把模型准备成可执行状态。这个阶段之后，模型已经常驻在推理模块中。

摄像头随后产生一帧图片。这张图片首先进入预处理模块，被 resize、颜色空间转换、归一化，并最终整理成模型要求的 Input Tensor。程序把这块 Tensor 数据交给 Runtime，然后调用一次推理接口。Runtime 根据模型中固定好的网络结构和权重执行 Forward，得到 Output Tensor。

假设输出 Tensor 表示各类别的概率，后处理模块就从中找到最高概率对应的类别，再通过标签映射把类别编号转换成“cat”。最后业务程序拿到的不再是 Tensor，而可能只是：

```text
label = "cat"
score = 0.92
```

于是完整过程实际上是：

```text
程序启动
  ↓
加载 model 文件
  ↓
创建并准备 Runtime
  ↓
────────────────────────────
摄像头产生一帧图像
  ↓
预处理
  ↓
Input Tensor
  ↓
Runtime 执行 Forward / Inference
  ↓
Output Tensor
  ↓
后处理
  ↓
label="cat", score=0.92
  ↓
业务代码使用结果
```

## 阅读真实部署代码时怎么快速定位

以后打开一个陌生的端侧模型部署模块，不需要一开始就理解所有类和 API。先沿着这条数据流找几个关键职责即可。

如果代码正在读取 `.onnx`、`.tflite` 或其他模型文件，创建 Session、Interpreter、Net 等对象，它大概率属于**模型加载和 Runtime 初始化**。

如果代码大量出现 resize、normalize、颜色转换、shape/layout 转换或把数据拷贝到输入缓冲区，它大概率属于**预处理与 Input Tensor 准备**。

如果代码调用某个 `run`、`invoke`、`forward`、`execute` 一类核心接口，而且这一调用前后分别连接输入和输出 Tensor，它大概率就是整条链路真正的**Inference / Forward 执行点**。

如果代码从输出 Tensor 中读取数组，再做 argmax、阈值筛选、NMS、标签映射、坐标转换等，它大概率属于**后处理**。

如果最后得到结构化对象、事件、识别结果或业务状态并交给 UI、控制逻辑、网络模块或者其他业务组件，那么这里已经离开模型推理层，进入了**业务消费层**。

所以阅读源码时最实用的思路不是先问“这个类叫什么”，而是不断问：**当前这段代码接收的数据是什么，它输出的数据又是什么？** 一旦能够判断数据目前处于“原始输入、Input Tensor、Output Tensor、业务结果”中的哪一种状态，通常就能快速确定这段代码位于整条部署链路的哪个阶段。

## 核心理解

端侧模型部署并不是简单地“加载一个模型然后调用一下”。它真正解决的是业务数据与神经网络之间的一整套衔接问题：模型文件保存训练结果，Runtime 负责把模型真正执行起来；预处理把原始业务输入转换为 Input Tensor；Forward/Inference 使用固定参数完成数值计算；Runtime 得到 Output Tensor；后处理再把这些数值转换为业务程序能够理解和使用的结果。

因此，最值得长期记住的不是某个框架的具体 API，而是下面这条稳定主线：

```text
初始化：
模型文件 → Runtime → 可执行模型

每次推理：
原始输入 → 预处理 → Input Tensor → Inference → Output Tensor → 后处理 → 业务结果
```

只要先抓住这条主线，以后无论遇到 TFLite、ONNX Runtime、MNN、NCNN 或其他端侧推理框架，具体 API 虽然不同，都可以先把代码重新映射回这几个职责位置，再继续理解框架特有的实现细节。

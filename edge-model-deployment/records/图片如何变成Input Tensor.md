# 图片如何变成 Input Tensor

## 来源脉络

[Tensor：端侧模型实际处理的数据是什么](Tensor基础.md)
→ 阅读时产生问题：“一个图片是如何被转换成一个 Tensor 的呢？”
→ 当前记录继续回答这个问题。

端侧图像模型并不会直接理解“这是一张 JPEG 图片”或者“这是摄像头画面”这样的业务概念。模型真正接收的是一块满足输入契约的 **Tensor**。因此，所谓“图片转换成 Tensor”，本质上不是把图片变成某种神秘的新信息，而是把图片中的像素数据解码出来，再按照模型要求重新调整尺寸、数值类型、数值范围和维度排列，最终组织成 Runtime 可以作为输入读取的 Tensor。

可以先把完整链路记成：

```text
JPEG / PNG / 摄像头帧
        ↓
      解码
        ↓
内存中的像素数据
        ↓
Resize / Crop 等尺寸处理
        ↓
颜色通道处理
        ↓
数值类型转换与归一化
        ↓
按照模型要求调整 Layout
        ↓
写入 Input Tensor
```

## 图片文件和像素数据不是一回事

如果输入是一张 JPEG 或 PNG 文件，文件本身通常是经过压缩编码的数据，并不是模型可以直接按像素读取的数组。程序首先要经过图像解码，得到内存中的像素数据。

以一张 RGB 图片为例，解码后可以把每个像素理解成三个颜色分量：

```text
像素 0：R = 255, G = 128, B = 0
像素 1：R = 100, G =  50, B = 20
...
```

所以从这一刻开始，图片已经可以看成一组有空间结构的数值。后面的预处理，主要就是把这组数值整理成模型训练时约定的输入格式。

如果输入本来就是摄像头解码后的一帧图像，那么程序可能已经直接拿到了 RGB、BGR、YUV 或其他像素格式，此时不一定存在单独的 JPEG/PNG 解码步骤，但仍然需要继续满足模型输入契约。

## 为什么通常需要先调整尺寸

模型输入的 Shape 往往是固定的。例如一个图像模型可能要求：

```text
shape = [1, 3, 224, 224]
```

这意味着单张输入图像最终必须对应 224 × 224 的空间尺寸。如果业务传进来的是 640 × 480 图片，就不能仅仅因为“它也是一张 RGB 图片”而直接交给模型。

程序通常会通过 Resize、Crop、Letterbox 等方式，把原始图像调整成模型需要的尺寸。具体使用哪一种方式取决于模型训练时的约定，因为不同处理方式会改变图像的几何关系。

例如：

```text
原始图片：640 × 480
        ↓ Resize
模型尺寸：224 × 224
```

经过这一步以后，每一个颜色通道都可以理解为一个 224 × 224 的二维数值矩阵。

## RGB 像素怎样形成 Tensor 的维度

假设模型要求 NCHW Layout，并且输入 Shape 为：

```text
[1, 3, 224, 224]
```

四个维度通常分别表示：

```text
N = 1      → 一次输入 1 张图片
C = 3      → RGB 三个颜色通道
H = 224    → 图片高度
W = 224    → 图片宽度
```

从概念上看，可以把 RGB 图像拆成三个通道：

```text
R 通道：
[
  [255, 100, ...],
  [ 80,  73, ...],
  ...
]

G 通道：
[
  [128,  50, ...],
  [ 60,  91, ...],
  ...
]

B 通道：
[
  [  0,  20, ...],
  [ 30, 120, ...],
  ...
]
```

这样就形成了 `3 × 224 × 224` 的数据，再在最前面加上 Batch 维度，就得到：

```text
1 × 3 × 224 × 224
```

也就是模型要求的四维 Input Tensor。

这里要注意，**Shape 本身只描述每个轴有多大，N、C、H、W 这些含义来自模型采用的 Layout 约定。** 如果模型要求 NHWC，那么 Shape 可能写成：

```text
[1, 224, 224, 3]
```

此时数据在各个轴上的排列顺序就不同。元素总数虽然一样，但程序写入 Tensor 的顺序必须符合模型要求。

## 为什么还要转换 dtype 和数值范围

原始图像像素通常使用 `uint8` 保存，每个颜色分量的数值范围一般是：

```text
0 ~ 255
```

但模型可能要求 `float32` 输入，并且训练时使用的是 `0.0 ~ 1.0` 的数值范围。于是程序就需要进行类型转换和归一化，例如：

```text
255 → 1.0
128 → 0.502
0   → 0.0
```

一种最简单的做法就是：

```text
normalized = pixel / 255.0
```

此时，原本的 `uint8` 像素值被转换成了模型预期的 `float32` 数值。

实际模型也可能采用其他归一化方式，例如继续减均值、除标准差，因此不能把 `pixel / 255.0` 当作所有模型的固定规则。**真正需要遵守的是模型训练阶段采用的输入约定。**

## 颜色顺序也属于输入契约

业务图像和模型使用的颜色顺序可能不同。例如某些图像库得到的是 BGR，而模型训练时使用的是 RGB。如果直接把 BGR 数据按 RGB 的语义写进 Tensor，Shape 和 dtype 都可能完全正确，但三个通道的数值含义已经错位。

因此图像预处理常常还包括：

```text
BGR → RGB
```

或者其他颜色空间转换。

这说明判断一个 Input Tensor 是否正确，不能只看 `224 × 224` 或 `float32`，还要同时检查通道顺序、Layout 和数值范围。

## 从程序角度看，最终发生的是“把数字写进一块 Tensor 内存”

经过尺寸、颜色、dtype、归一化和 Layout 调整后，程序已经得到了模型需要的那组数值。最后一步就是按照 Runtime 提供的输入接口，把这些数值写入 Input Tensor 对应的内存。

因此，从端侧 C/C++ 代码的角度看，经常会出现这样的逻辑结构：

```text
读取/获取图像
    ↓
resize
    ↓
颜色转换
    ↓
uint8 → float32
    ↓
normalize
    ↓
HWC → CHW（如果模型要求 NCHW）
    ↓
copy / write 到 input tensor buffer
```

不同 Runtime 的 API 名称会不同，但只要代码在做这些事情，本质上都属于同一个阶段：**构造满足模型输入契约的 Input Tensor。**

## 为什么这整个过程叫“预处理”

模型训练完成以后，网络结构和权重已经固定。模型并不会因为业务输入尺寸不同、通道顺序不同或者数值范围不同，而主动替你猜测应该怎样转换。

因此，预处理承担的是模型和业务数据之间的适配工作：

```text
业务世界中的图片
        ↓
      预处理
        ↓
模型世界中的 Input Tensor
```

预处理最重要的目标并不是“把图片处理得更漂亮”，而是让推理阶段看到的数据，在格式和数值语义上与模型训练时看到的数据保持一致。

如果预处理约定错误，即使 Runtime 能成功执行推理，也可能得到完全错误的结果。例如：

```text
模型要求 RGB，实际输入 BGR
模型要求 float32，实际按 uint8 解释
模型要求 NCHW，实际按照 NHWC 写入
模型训练时做过归一化，部署时却没有做
```

这些情况都可能出现“代码能跑、推理也没有报错，但结果很差”的现象。

## 内容小结

图片转换成 Tensor，可以理解为两层变化。第一层是**把图片变成可计算的像素数值**：压缩图片先解码成 RGB、BGR 等像素数据。第二层是**把像素数值整理成模型规定的数据结构**：按照模型要求完成尺寸调整、颜色通道转换、dtype 转换、归一化和 Layout 调整，最后写入具有指定 Shape 的 Input Tensor。

以常见的 `[1, 3, 224, 224]`、`float32`、NCHW 图像模型为例，可以把链路记成：

```text
JPEG / PNG
    ↓ 解码
RGB 像素
    ↓ Resize 到 224 × 224
调整颜色通道
    ↓
uint8 → float32
    ↓
按照训练约定归一化
    ↓
整理成 NCHW
    ↓
[1, 3, 224, 224] Input Tensor
```

所以，“图片变成 Tensor”并不是图片内容发生了本质变化，而是**同一组视觉信息被转换成神经网络约定的数值表示形式**。这正是图像模型预处理阶段最核心的职责。

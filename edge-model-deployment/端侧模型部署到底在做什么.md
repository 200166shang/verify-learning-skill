# 端侧模型部署到底在做什么

如果把训练阶段和部署阶段分开看，端侧部署真正关心的并不是“模型是怎么学会的”，而是“一个已经训练好的模型，如何在设备上稳定地接收真实输入、完成推理，并把输出转换成业务可以使用的结果”。因此，理解端侧部署时，可以先把它看成一条完整的数据处理链，而不是一堆孤立的深度学习术语。

这条链路可以先概括为：

```text
模型文件
   ↓
Runtime 加载
   ↓
准备原始输入
   ↓
预处理
   ↓
Input Tensor
   ↓
Forward / Inference
   ↓
Output Tensor
   ↓
后处理
   ↓
业务结果
```

## 模型真正接收的是 Tensor

模型不会直接理解“图片”“声音”“文本”这些业务概念。进入模型之前，数据最终都需要表示成 Tensor。Tensor 可以理解为带有形状和数据类型的多维数组，而 shape、dtype、batch 等信息决定了这块数据在模型中的组织方式。

例如，一张图片在业务代码里可能最开始是 JPEG、PNG，或者来自摄像头的一帧图像，但模型真正看到的通常是类似 `[1, 3, 224, 224]` 的浮点 Tensor。这里的每一个维度都有明确含义，因此端侧部署代码里经常会出现尺寸调整、通道转换、内存排列和数据类型转换等操作。它们并不是外围杂务，而是在把业务数据转换成模型能够接收的输入格式。

## 模型文件保存的是已经学到的推理能力

训练过程中，模型通过 Forward 得到输出，再通过 Loss 衡量结果与目标之间的差距，随后经过 Backward 计算梯度，并更新参数。这个过程会反复进行，直到模型参数逐渐收敛。

端侧部署时，训练过程通常已经结束。设备拿到的是已经训练完成的模型文件，其中包含模型推理所需的参数，以及能够描述模型计算过程的网络结构或计算图信息。部署程序的任务不是继续训练，而是把这些内容交给对应的推理 Runtime，让 Runtime 能够真正执行这张计算图。

因此，在部署语境里，最核心的动作通常是 Inference，也就是 Forward。模型参数在正常推理过程中保持不变，程序只需要不断接收新的输入，然后计算新的输出。

## 为什么原始输入不能直接交给模型

现实世界中的数据格式和训练时模型看到的数据格式往往并不一致。例如摄像头得到的图像可能是不同分辨率、不同像素格式、不同颜色通道顺序，而训练时模型可能固定使用某一种尺寸、RGB 顺序，并且要求像素值经过归一化。

所以在进入模型之前，需要做预处理。预处理的本质不是“美化数据”，而是把真实业务输入恢复成模型训练时约定的输入分布和数据格式。

对于图像模型，常见预处理可能包括 resize、crop、颜色通道转换、归一化、数据类型转换以及 Tensor layout 调整。经过这些处理后，业务数据才真正变成可送入模型的 Input Tensor。

## 推理阶段发生了什么

当 Input Tensor 准备完成后，Runtime 会按照模型中保存的计算结构执行 Forward。输入 Tensor 会依次经过网络中的各层和算子，模型参数参与计算，最终产生一个或多个 Output Tensor。

从端侧部署代码的角度看，这一步往往看起来非常简单，例如调用一次 `run`、`invoke`、`forward` 或类似接口。但这个接口背后，Runtime 实际承担了模型解析、执行环境准备以及底层计算执行等工作。具体 Runtime 如何调度算子、管理内存或选择硬件后端，属于更深入的实现细节，不影响当前对主链路的判断。

## 为什么模型输出还不能直接给业务使用

模型产生的通常仍然是 Tensor，而不是直接的业务答案。

例如分类模型可能输出一组类别分数，目标检测模型可能输出大量候选框及其置信度，分割模型可能输出每个像素对应的类别概率。业务真正需要的却可能只是“这是猫”“发现一个人，位置在这里”或者一张最终的分割掩码。

所以模型输出之后还需要后处理。后处理负责把 Output Tensor 转换成业务语义。它可能包括 softmax、argmax、阈值过滤、坐标转换、NMS 或结果格式封装等步骤。

因此，预处理和后处理分别站在模型的两侧：预处理负责把业务世界的数据翻译成模型能够理解的 Tensor，后处理负责把模型输出的 Tensor 再翻译回业务世界能够理解的结果。

## 真正的端侧程序怎样把这些环节串起来

真实端侧程序通常需要区分两个生命周期。初始化阶段一般只执行一次：程序读取模型文件，创建 Runtime 以及对应的 Session、Interpreter 或执行上下文，让模型进入可执行状态，并准备必要的输入输出资源。模型文件本身只是静态的网络结构和参数描述，真正负责执行模型的是 Runtime，因此模型通常不会在每处理一帧数据时重新加载。

初始化完成后，程序进入反复执行的推理阶段。每获得一份新的摄像头图像、音频或其他业务输入，就先按照模型的输入契约进行预处理，形成满足 shape、dtype、layout 和数值范围要求的 Input Tensor；随后把 Tensor 交给已经初始化好的 Runtime，触发一次 Forward / Inference；Runtime 按照固定的网络结构和训练完成的权重进行数值计算并产生 Output Tensor；最后由后处理把这些数值结果解释成类别、检测框、特征向量或其他业务数据，再交给上层逻辑使用。

因此从程序生命周期来看，更准确的结构是：

```text
初始化：
模型文件 → Runtime → 可执行模型

每次推理：
原始输入 → 预处理 → Input Tensor
        → Inference / Forward
        → Output Tensor → 后处理 → 业务结果
```

以后阅读真实部署代码时，可以先不纠结框架的类名，而是观察数据正在发生什么变化：读取模型并创建执行对象通常属于初始化；resize、normalize、颜色和 layout 转换通常属于预处理；`run`、`invoke`、`forward`、`execute` 一类调用通常是推理执行点；从输出数组做 argmax、阈值筛选、NMS、标签或坐标映射通常属于后处理；当结果被封装成业务对象并交给 UI、控制逻辑或其他模块时，就已经进入业务消费层。只要能判断当前数据是原始输入、Input Tensor、Output Tensor 还是业务结果，就能快速把陌生代码映射回整条部署链路。

## 当前对端侧部署的整体理解

端侧模型部署的核心不是重新训练模型，而是把一个已经训练完成的模型变成设备上可以持续运行的推理能力。模型文件保存网络结构和训练得到的参数，Runtime 负责把这些静态信息真正执行起来；预处理负责把业务输入转换成模型要求的 Input Tensor；Forward / Inference 使用固定参数完成计算并产生 Output Tensor；后处理再把数值结果转换成业务程序能够理解的数据。

因此，面对一个陌生的端侧部署模块时，可以先沿着“模型加载 → 输入准备 → 推理 → 输出读取 → 后处理 → 业务消费”寻找主流程，再逐渐进入具体 Runtime、硬件后端和性能优化等实现细节。这样阅读代码时，具体框架 API 即使不同，也仍然能够映射回同一条稳定的部署主线。
